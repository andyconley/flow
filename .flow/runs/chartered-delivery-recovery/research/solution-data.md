# Solution data note: chartered (v8) recovery durable-state design

## 1. Attempt status

Recommended: do **not** add a new `attempts.status` enum value for "interrupted, recoverable." Observed: `attempts.status` (`execution_ledger.py:57`) is free TEXT, and `finish_attempt` only recognizes `{completed, failed, denied, unknown}` as terminal (`:1236`), requiring the row to already be `started` before transitioning (`:1242`). `decide()`/`decide_manager_call` treat `status == "started"` as the live/open condition (`:318-321`, `:505-508`). A v8 attempt that is mid-flight but has an unresolved action is *already* representable as `status="started"` with one or more `actions`/`manager_calls` rows at `status IN ('started','unknown')` (`_unresolved_action`, `:283-291`). Chunk 1/2 both work by never calling `finish_attempt` while `_unresolved_action` is non-empty.

Difference from `unknown`: `unknown` (per `finish_attempt:1236,1247-1249`) is a **terminal, sealed** attempt state — it writes `receipt_path` and requires parity between "uncertain sends exist" and "status==unknown" (`:1247`). It is a closed receipt, not a pause. The recommended v8 rule is the inverse: **never call `finish_attempt` at all** while `_unresolved_action(db, attempt_id)` is non-null for a v8 attempt — the attempt just stays `started`, non-terminal, with no receipt. This is additive: it only changes when v8 callers invoke `finish_attempt`, not the ledger's accepted statuses. v5's existing `unknown`-terminal-then-continuation-epoch pattern (`:1252-1276`, `_magentic_continuation_open:227-233`) is untouched; v6/v7 never reach this branch (`row[1] in {5,6,7,8}` at `:1244` already includes 8, so the parity check at `:1247` must be scoped to exclude v8's "stay open" case — recommended: add `and status != "started"` guard so v8 simply skips `finish_attempt` rather than the check being loosened).

## 2. Recovery records

Recommended: no new table. Reuse the append-only `events` table (`:90-93`) for the claim fact — `_claim_recovery_locked` already emits `recovery_claimed` with `{actor, generation}` (`:275`) — and the existing `recovery_resolutions` table (`:98-104`) for every operator resolution relied on. The single receipt is built by reading: `attempts.owner_generation` (current fencing generation, `:59`), all `events` rows with `event='recovery_claimed'` for that `attempt_id`, and all `recovery_resolutions` rows for that `attempt_id`.

Idempotency key: `recovery_resolutions` is keyed by `resolution_digest UNIQUE` (`:102`) but only *app-checked* per `action_id` via `SELECT ... WHERE action_id=?` (`resolve_unknown:906`), not DB-enforced. Recommended (additive): add `CREATE UNIQUE INDEX IF NOT EXISTS recovery_resolutions_attempt_action ON recovery_resolutions(attempt_id, action_id)`, mirroring the existing tolerant-migration pattern at `:179-182` (try unique, fall back to non-unique index on `IntegrityError` for legacy rows).

Mutual exclusion: already present. `claim_recovery` takes the exclusive file lock `send_lock()` (`:194-205`) around `_claim_recovery_locked`'s `BEGIN IMMEDIATE` transaction (`:246-250`), so two concurrent recovery commands serialize; the second sees the already-bumped `owner_generation`. Gap (recommended fix for Req 2's "no second reconciliation pass"): `_claim_recovery_locked` unconditionally increments `owner_generation` on every call (`:265-266`) with no check for "nothing left unresolved." Recommended: before bumping, check `_unresolved_action`; if none and the attempt is not fresh from a genuine interruption, return the current `(recovery_version, owner_generation)` unchanged instead of fencing again.

## 3. Superseded attempts

Recommended new terminal status `"superseded"`, added to `finish_attempt`'s accepted set (`:1236`, additive union) but exempted from the uncertain/status parity rule at `:1247` (superseding intentionally leaves `unknown`/`started` actions fenced-but-unresolved, unlike `unknown`). `reason` records the fencing lead generation and whether resume or supersede triggered it; `receipt_path` may stay `NULL` — Req 10 asks for a terminal *record*, not a full receipt, so no new receipt-validation burden on `_validate_magentic_receipt`. This is invoked from `delivery_control.py`'s `change_lead_claim` (`:210` per brief), not from this file.

## 4. Attempt lineage

Recommended additive table `attempt_lineage(attempt_id TEXT PRIMARY KEY REFERENCES attempts, predecessor_attempt_id TEXT NOT NULL REFERENCES attempts, predecessor_terminal_status TEXT NOT NULL, fenced_by_generation INTEGER NOT NULL, created_at TEXT NOT NULL)`, idempotency key `UNIQUE(attempt_id, predecessor_attempt_id)`. Populated when `create_attempt` opens a successor attempt.

Observed: `create_attempt` (`:235-244`) performs a bare `INSERT` with no query against existing rows for the same `work_id` — there is no dedupe check before the insert at `:243`. **A second attempt for the same logical delivery (`work_id`) is allowed today**, confirmed at `execution_ledger.py:235-244`. Policy caps in `decide()` constrain concurrent/allowed *actions* by `work_id` (`:344-352`) but never block a second `attempts` row. This matches the brief's restart-from-baseline design and answers the requirements.md open question: yes, a successor attempt can be created; recommended addition is an app-level (not DB-enforced) check that the predecessor is actually terminal (`superseded`/`failed`/`unknown`) before linking it in `attempt_lineage`.

## 5. Evidence reuse

`verifier_inputs.test_digest` (`:143`) plus `diff_digest` (`:142`) and the immutable `envelope_json` (`:56`, unchanged per envelope-immutability constraint) durably fix *which* diff and *which* recorded test-output hash were bound before the send. That proves reuse is safe against re-verification of the diff (Req 6). It is **not confirmed in this file** whether the exact test command/invocation is itself content-addressed inside `envelope_json`'s `job_contract`, or only its digest is retained — `verifier_inputs.input_json` (`:143`) is the verifier's structured input, not necessarily the shell/test command. Recommended: confirm in `delivery_gateway.py:prepare_chartered_delivery` (~250-420, not read here) that the test command is part of the envelope (and thus already pinned by `envelope_digest`); if not, add an additive column to `verifier_inputs` (e.g. `test_command_digest`) recorded at `bind_verifier_input`/`prepare_verifier_send` time (`:626-667`, `:723-754`) so recovery never has to guess the command used to produce `test_digest`.

## 6. Migration

Additive only, matching the existing pattern: new tables via `CREATE TABLE IF NOT EXISTS` inside the same `executescript` block (`:54-150`); the `attempt_lineage` table and the `recovery_resolutions` unique index follow the tolerant try/except pattern already used for `actions_attempt_kind_sequence` (`:179-182`). No `ALTER TABLE` is needed for status values since `attempts.status`/`reason` are free TEXT (`:57`). Old-database fixture impact: none — pre-v8 databases have no `execution_protocol_version=8` rows, so `superseded`/lineage logic never fires against them, and the existing `PRAGMA table_info` presence-check idiom (`:154-173`, `:183-187`) already proves ALTER-based columns are safe against first-slice fixtures. No durable migration-history table is needed or wanted: schema evolution here is column/table-presence-checked at connect time (`:151-187`), which is itself the project's migration-history mechanism; adding a separate versioned migrations table would be a new, non-additive process this codebase doesn't use.

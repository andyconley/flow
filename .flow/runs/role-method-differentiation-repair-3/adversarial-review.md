# Adversarial review: three-role expertise expansion

- Work item: `role-method-differentiation-repair-3`
- Reviewer roles: product-manager, business-analyst, solution-architect,
  test-engineer
- Status: Dispositioned; explicit engineer approval remains pending

## Evidence inventory

- **Already exists:** repair-2 approved requirements, frozen manifest and
  scorecard, eight raw response envelopes, formal quality/test reviews, current
  role bodies/corpora/configuration, the original expansion evidence, five
  repair-3 research notes, a source-status inventory, and the repair-3 draft.
- **Partially covered:** the three-role expansion has bounded behavioral
  evidence but no adoption/support metric; future PM/QR candidate value and
  source fit remain unverified.
- **Checked and genuinely absent:** no PM/QR passing behavioral record, no user
  deadline that warrants a third immediate experiment, no existing
  provenance-only admission policy, and no approved supersession of the prior
  all-five relationship.
- **How searched:** reviewers read both failed evidence generations, current and
  frozen role bodies, architecture/ADR/configuration/test surfaces, all repair-3
  research, and the complete working-tree diff. The coordinator froze and
  independently verified 112 protected per-file hashes and a three-role evidence
  map. Archive retrieval itself was unavailable and is not credited with these
  manually inspected findings.

## Product challenge

- **Question:** Should repair-3 release the proven subset, retain all five under
  separate provenance/behavior claims, or pay for another candidate screen?
- **Finding:** A narrow three-role release has an evidence-backed technical
  outcome and a reversible path. No measured PM/QR need justifies retaining
  unproven prompt cost or funding 24 exploratory envelopes now. The first draft
  needed evidence-correct success language, an explicit two-axis tradeoff, and a
  trigger for later exploration.
- **Disposition:** Requirement and success language now make no adoption claim,
  defer rather than invalidate the two-axis policy, and require a named workflow
  need, verified source, and approved fixed budget before candidate screening.

## Requirements challenge

- **Question:** Can the draft unambiguously prove the selected user-visible
  outcome and preserve every historical record?
- **Finding:** The initial draft left the removal/two-axis choice unapproved,
  used aggregate preservation, had ambiguous live-client semantics, combined
  two mutation guards, omitted the base-role compatibility outcome, and made
  scope searches too broad.
- **Disposition:** The draft now states that PM/QR remain invocable as unchanged
  base roles after sync; binds preservation to a 112-file pre-mutation inventory
  and a named three-role evidence map; makes both live-client observations hard
  gates; requires separate exclusion and retention mutations; and confines
  current-claim searches to planned active surfaces. The removal boundary still
  requires explicit engineer approval, as intended by the definition gate.

## Architecture / capability challenge

- **Question:** Does active PM/QR removal violate ADR 0008 or require a new
  status architecture and solutioning phase?
- **Finding:** ADR 0008 governs JSON-LD form, citation pinpoints, and role
  ownership; it does not require every authored corpus to remain active. The
  uncommitted PM/QR additions can be reversibly removed without changing storage,
  rendering, retrieval, or routing. The initial preservation language did not
  explicitly include prior run-level reviews and source verification.
- **Disposition:** ADR 0008 remains applicable and honored. The complete prior
  run and both evidence roots now appear in the per-file inventory. The selected
  implementation has one clear path and may route directly to `flow-plan`; only
  a reopened general two-axis policy would require `flow-solution`.

## Conditional role challenges

- **Role:** test-engineer
- **Question:** Can the criteria reject a wrong narrowed release without relying
  on substring tests, aggregate counts, or static smoke?
- **Finding:** Historical README edits conflicted with tree immutability, live
  verification was both a gate and limitation, and the evidence/mutation/scope
  oracles were initially incomplete.
- **Disposition:** New release evidence must live outside protected roots; live
  Claude and Codex observations are blocking; the frozen map names all four
  records and hashes for each passing role; inactive PM/QR is structurally
  defined across manifest, loader, vocabulary, renderer, and base body; and two
  independent restored mutations are required. Recheck found all testability
  issues resolved.

## Approval impact

- **Requirement changes:** added base-role compatibility, exact evidence
  inventory/map, run-local admission rationale, new-summary location, and a
  resolvable candidate-screen trigger.
- **Acceptance criteria changes:** added per-file preservation, exact three-role
  record mapping, structural inactivity, separate mutations, blocking live
  checks, bounded active-document search, and explicit change-surface review.
- **Non-goal changes:** the general provenance-only policy is deferred for lack
  of measured value rather than rejected as invalid.
- **Assumption changes:** technical evidence correctness is the release outcome;
  adoption or global agent improvement is not claimed.
- **Next-lane impact:** `flow-plan` after explicit engineer approval. The
  approval supersedes only repair-2's all-five release relationship, never its
  scores, stopping rule, or evidence.
